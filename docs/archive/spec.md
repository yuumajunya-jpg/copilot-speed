# Copilot 送信遅延を軽減するブラウザ拡張機能の仕様案

作成日：2026-11-13

本書は [調査結果](../investigation.md) をもとにした設計案である。
対象の内部関数にアクセスできるか、最適化で実際に遅延が減るかは、実証前である。

追記：現行の介入経路と検証範囲は [実装資料](../implementation.md) に記載した。
以下は設計時の案であり、実アプリでの性能目標は未達成として扱う。
0.2.0 では利用者の方針に従って計測機能と試験用 UI を削除したため、本書の計測関連項目は現行仕様には含めない。

## 1. 推奨する方針

**購読解除の処理量を減らす拡張機能**を候補とし、最初に置換可能性と効果を検証する。
拡張機能を入れれば改善すると現時点で保証することはできない。
ページ内部の購読管理に限定して介入できることを、製品化の前提とする。

開発は、計測用の試作、対象ストアの最適化、環境別の対応確認の順に進める。
計測だけの段階を「高速化機能」として扱わない。
置換経路を確保できなければ、購読管理の最適化は見送り、制約を報告する。

## 2. 調査結果と設計への影響

| 区分 | README の内容 | 設計への影響 |
|---|---|---|
| 確認済み | 個人用 Copilot の Chrome トレースで、送信クリック処理が約 10.33 秒 | まず送信時の画面反映までの遅延を評価する |
| 確認済み | 購読解除関数の推定自己時間が約 9.20 秒 | 対象ストアの解除処理を優先して検証する |
| 確認済み | 通知先を配列で管理し、解除に `indexOf` と `splice` を使用 | 探索と配列の詰め直しを避ける管理方式を候補にする |
| 確認済み | レイアウト計算は約 0.02 秒 | CSS による描画省略を主対策にしない |
| 未確認 | 数式が購読数や解除回数を増やすか | 数式量と会話長を分けて比較する |
| 未確認 | Enter 送信、会社の Vivaldi、Microsoft 365 Copilot Chat の原因 | 個人用での結果をそのまま適用しない |
| 未確認 | 対象ストアの公開範囲、差し替え可能な入口 | 最適化コードの設計前に実証する |

購読数を N、まとめて解除する件数を K とすると、配列の探索と削除を繰り返す処理量は最悪で O(KN) になり得る。
K が N と同程度なら O(N²) になり得るが、今回の実測でこの増え方を確認したわけではない。
購読数、解除件数、解除順序を追加で確認する必要がある。

## 3. 対策候補の比較

| 候補 | 今回の原因に対する見込み | 採用判断 |
|---|---|---|
| 対象ストアの購読管理を最適化 | 探索と詰め直しを削減できれば、主因に直接作用する | 実証を優先する |
| 古い発言を CSS で折り畳む、`content-visibility` を指定 | 描画負荷を減らせても、購読や React の解除処理は残る | 初期版には含めない |
| 数式を DOM 上でテキストや画像に置き換える | 見た目を変えても、React が持つ購読は減るとは限らない | 採用しない |
| 古い発言の DOM を削除、別領域へ移動 | React の管理状態との不整合が起き得る | 採用しない |
| 新しい会話へ移る操作の補助 | 会話が短い状態に戻ることで軽減する可能性はあるが、文脈が変わる | 最適化が成立しない場合の別案とする |
| 送信前に会話を再読み込み | 購読の再生成が必要で、同じ遅延が再発する可能性がある | 自動実行しない |

React の公式文書も、React が管理する DOM の子要素の追加や削除によって、表示の不整合やクラッシュが起きる可能性を説明している。[参照](https://react.dev/learn/manipulating-the-dom-with-refs)

## 4. 対象範囲

初期の実証対象は、Windows の Chrome と個人用 Copilot とする。
会社の Vivaldi と Microsoft 365 Copilot Chat は、別のページ構造と内部実装を持つ可能性があるため、個別に検証する。
ブラウザ名、バージョン、実際のチャット URL、フレーム構成、対象スクリプトの識別情報を対応表に記録する。
現時点ではブラウザの最低バージョンや会社向けの対象 URL を確定しない。

会話内容、数式表現、回答品質、送信先、サーバー側の会話履歴を維持する。
回答生成そのものの時間やネットワーク待機の短縮は対象外とする。
非公開の Copilot API を使った独自チャット画面は作らない。

## 5. 実証で確認する条件

### 5.1. 原因の再確認

同じ会話状態でクリック送信と Enter 送信を記録し、対象関数の呼び出し回数と時間を調べる。
対象ストアごとに、最大購読数、登録数、解除数、送信前後の残存数を計測する。
通常利用で解除される購読と、解除されずに残る購読を区別し、購読リークの有無も調べる。
本書ではリークがあるとは仮定しない。

### 5.2. 介入経路

対象スクリプトとストア生成箇所を調べ、購読登録が始まる前に差し替えられる入口があるかを確認する。
グローバルに公開されたストアや、ページが公開しているモジュール登録経路が候補になるが、存在は未確認である。
圧縮後の短い関数名や、`indexOf` を使用しているという特徴だけで対象を決めない。

拡張機能はページと実行環境を共有する `MAIN` world を選べるが、それだけでクロージャ内のローカル変数や関数にアクセスできるようにはならない。
通常の content script は `ISOLATED` world で動くため、内部ストアへの介入部分と、拡張機能の設定や画面表示を扱う部分を分ける。[Chrome の実行環境の説明](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)

初期化時の介入には `document_start` を使う。
この指定と `MAIN` world は manifest の content script で設定できる。[manifest の仕様](https://developer.chrome.com/docs/extensions/reference/manifest/content-scripts)
導入直後の既存タブや設定変更後は、再読み込み後に適用する。
読み込み順、遅延ロード、キャッシュからの復帰も実証する。

### 5.3. 実装へ進む判断

次の条件をすべて満たした場合に、最適化機能を実装する。

- 問題のストアだけを識別し、購読開始前に介入できる。
- 元の登録、通知、解除の動作を確認できる。
- 対応済みの実装と未対応の実装を、書き換え前に判別できる。
- 比較試験で送信遅延と購読解除時間が減り、操作上の不具合がない。

対象が閉じたスコープ内にあり、限定した介入経路を確保できない場合は、この方式を中止する。
ページ全体の `Array.prototype.indexOf`、`splice`、React の内部構造を一律に書き換えて代用しない。
サイトの JavaScript を取得し、文字列置換して `eval` で実行する方式も採用しない。
Manifest V3 での公開を考える場合、外部から取得した実行コードは Chrome の配布規則にも抵触し得る。[Chrome の外部コードに関する説明](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code)

## 6. 購読管理の最適化仕様

対象ストアの登録、通知、解除を一体で置き換え、解除だけを別の管理方式にしない。
既存の解除関数が古い配列を参照し続ける事態を避けるため、動作中のストアを途中で移行しない。
対象ストアの処理以外は変更しない。

候補となる実装は、登録ごとのノードを持つ双方向リストとする。
登録時に返す解除関数がノードを直接参照すれば、探索と後続要素の詰め直しを避け、登録と解除を原則 O(1) にできる。
通知時の走査は O(N) とする。
ただし、通知対象のスナップショット作成が必要なら、その追加コストも比較に含める。
実際のデータ構造は、元の動作を再現できるものを実証後に確定する。

単純な `Set<callback>` への置換は仕様にしない。
同じ関数を複数回登録した場合に登録数が変わるほか、通知中の追加や削除の扱いが元の実装と一致するとは限らないためである。

| 保存する動作 | 確認する例 |
|---|---|
| 登録順と通知順 | A、B、C を登録した際の実行順 |
| 重複登録 | 同じ関数を 2 回登録し、片方だけ解除 |
| 解除関数の動作 | 同じ解除関数を 2 回呼ぶ、通知後に解除 |
| 通知中の変更 | 自己解除、次の通知先の解除、新しい購読の追加 |
| 再入 | 通知先から再び状態を更新 |
| 引数と戻り値 | `this`、コールバック引数、登録関数の返り値 |
| 例外処理 | ある通知先が例外を投げた場合の後続処理 |
| 解放 | 解除したノードやコールバックへの参照を保持し続けない |

解除を遅延実行する方法や、一部の解除を省略する方法は使わない。
破棄済みの部品への通知、重複通知、メモリ保持を避ける。

## 7. 利用者向け機能

拡張機能のポップアップに、現在の状態とサイト単位の有効設定を表示する。
状態は「計測のみ」「最適化適用中」「未対応」「再読み込み待ち」「エラーで停止」とする。
計測のみの状態では、改善済みと誤認させる表示をしない。

利用者は、最適化の有効設定、診断の開始と停止、診断結果の保存、診断記録の削除を行える。
初回の試作は計測のみとし、検証済みの環境で最適化を有効にする。
対応済み環境での既定有効化は、受け入れ試験を通過した後に判断する。

「停止」は、次回の読み込みから最適化を適用しない設定にする。
すでに動作しているストアを、その場で元のデータ構造に戻すことはしない。
画面内の入力を保持したまま設定を変更できるようにし、再読み込みは利用者が実行する。
会話の自動削除、自動送信、自動再読み込みは行わない。

## 8. 計測仕様

### 8.1. 送信遅延

主指標は、**送信操作から自分の発言が会話欄に現れるまでの時間**とする。
補助指標として入力欄が空になるまでの時間、送信直後の最大タスク時間、購読解除の合計時間と件数を記録する。
回答の先頭が表示されるまでの時間は、サーバー処理を含む別指標として扱う。

起点には、送信クリックまたは送信に対応するキーイベントの `timeStamp` を使う。
イベントリスナーに到達した時刻も記録し、メインスレッドが塞がっていた時間を見落とさないようにする。
日本語 IME の確定 Enter、改行、送信無効時の操作、送信キャンセルは、正常な送信と分ける。
イベントの取り消しや再送によって計測しない。

発言の追加と入力欄の変化は、対象範囲を絞った DOM 監視で検出する。
監視コールバックの実行時刻は実描画の時刻と一致しないため、DOM で観測した反映時間として報告する。
実描画との差は受け入れ試験のトレースで確認する。
一定時間内に発言を検出できない場合は「未観測」として残し、成功例の集計から黙って除外しない。

### 8.2. 計測負荷

通常時は数値カウンター中心とし、全 DOM の繰り返し走査や、全解除処理でのスタック文字列生成を避ける。
購読数や関数別の時間は、対象ストアへの診断用の介入が可能な場合だけ記録する。
取得できない項目を 0 と表示せず、「取得不可」と表示する。
診断イベントはタブごとの上限付きバッファに保持し、初期案は直近 200 件とする。

Long Tasks API は利用可能な場合の補助計測に使う。
50 ms 以上のメインスレッド占有を観測できるが、これだけで関数別の購読解除時間はわからない。
対応状況を実行時に確認し、詳細な原因分析には DevTools の CPU トレースを使う。[Long Tasks API の説明](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceLongTaskTiming)

## 9. 構成と権限

| 構成要素 | 役割 |
|---|---|
| `manifest.json` | Manifest V3、確認済みの対象 URL、実行タイミングを宣言 |
| 分離環境の content script | ページ判別、送信計測、最適化側から受け取る数値の検証 |
| `MAIN` world のスクリプト | 対応実装の判定、対象ストアへの限定した介入、数値カウンター |
| 環境別アダプター | 個人用と Microsoft 365 の検出条件や介入方法を分離 |
| ポップアップと設定処理 | 状態表示、サイト単位の設定、診断の保存 |

権限は設定用の `storage` と、確認済みのチャットページへの content script のアクセスを基本とする。
動的登録を採用する場合に限り、`scripting` と必要なサイト権限を追加する。
`<all_urls>`、`debugger`、Cookie、閲覧履歴への権限は要求しない。
会社向けページがフレーム内で動く場合は、その実際のオリジンと対象フレームを確認してから対応する。
全フレームに無条件で介入しない。

会話本文、入力内容、数式の原文、認証情報は診断ログに保存しない。
診断にはブラウザの種類とバージョン、アダプター識別子、処理件数、時刻、所要時間、適用状態を記録する。
会話 ID、クエリ文字列、利用者を識別する URL は含めない。
診断ファイルは利用者の操作でローカルに保存し、外部送信や同期保存は行わない。

ページと分離環境の通信は、定義済みの状態値と上限付きの数値だけを受け付ける。
ページ側からの通知は信頼せず、任意コード、任意 URL の取得、任意の設定変更を依頼できる経路を作らない。
最適化コードと対応条件は拡張機能に同梱し、更新で配布する。

## 10. 更新と異常時の動作

アダプターは、確認済みのビルド識別情報と介入入口の構造を組み合わせて対象を判別する。
具体的な識別方法は実証で得られた入口に応じて定める。
識別情報を取得できない、構造が違う、二重適用を検出した、初期化に失敗した場合は、改変せず「未対応」または「エラーで停止」と表示する。

適用後の異常では、新たな介入を止め、次回読み込み時の最適化を無効にする。
ページがすでに変更された状態から完全に回復できるとは保証せず、再読み込みが必要なことを表示する。
障害発生時にも自動でページを再読み込みしない。
Microsoft 側で対象処理が改善された場合は、比較測定を行い、不要になった介入を廃止する。

## 11. 検証と受け入れ基準

### 11.1. 比較条件

拡張なし、計測のみ、最適化ありの 3 条件を、同じ PC、ブラウザ、アカウント、会話の初期状態で比較する。
送信すると履歴が増えるため、各試行では同じ開始状態へ戻すか、同じ手順で作った比較用会話を使う。
同じ会話で単に連続送信した値を、有効化前後の比較にしない。
他の拡張機能は条件をそろえ、まず無効化した条件で原因を切り分け、その後に通常の利用構成でも確認する。

| 軸 | 比較する条件 |
|---|---|
| 会話量 | 短い会話、遅延が再現する長い会話 |
| 数式量 | 数式なし、少量、多量。会話量をできるだけそろえる |
| 操作 | クリック、Enter、IME 確定、Shift+Enter |
| 履歴操作 | 再読み込み、過去の会話を開く、会話切替、戻ると進む |
| 回答操作 | 生成中、停止、再生成、発言編集、コピー、数式選択 |
| 環境 | 個人用の Chrome、会社の Vivaldi と Microsoft 365 を別集計 |

各主要条件で最低 10 回測定し、中央値、最大値、失敗件数を報告する。
大量の試行を自動送信して会話を作ることはせず、用意した検証用会話を使う。
最適化による登録、解除の動作は、実証で確認した元のストアと同じ操作列を使う比較テストで検証する。

### 11.2. 暫定目標

以下は実測値ではなく、実証で採否を判断するための目標とする。

- 遅延を再現できる会話で、送信から発言追加までの中央値を 50% 以上短縮する。
- 同条件で、対象ストアの購読解除の合計時間を 80% 以上短縮する。
- 短い会話で、送信遅延の中央値の悪化を `max(対照の 10%, 20 ms)` 以内に収める。
- 計測のみの条件も同じ悪化幅以内に収め、計測自体が負荷の主因にならないことを確認する。
- 発言の消失、二重送信、通知の欠落、数式やコピーの破損を発生させない。
- 会話切替と送信を繰り返しても、解除済み購読が増え続けないことを確認する。
- 未対応のビルドでは、最適化を適用しない。

時間の短縮だけで合格にしない。
動作の同等性、未対応時の非適用、停止後の再読み込みによる復帰を確認してから、その環境を対応済みとする。

## 12. 最初に作るもの

最初の成果物は、個人用 Copilot 向けの計測用拡張と、対象ストアの介入可否を示す実証記録とする。
記録には対象コードの識別方法、登録前の介入経路、通知の動作、計測結果、適用できない条件を残す。
現時点ではアプリ本体の配布コードがリポジトリにないため、介入先の具体的な識別子や差し替えコードは本書で確定しない。

実証が通れば購読管理の最適化を実装し、個人用で受け入れ試験を行う。
その後、会社の環境で原因と介入経路を確認し、別アダプターとして対応する。
実証が通らない場合は最適化機能を実装済みと扱わず、新しい会話へ移る補助など、文脈の扱いを利用者が選べる別仕様を検討する。
